# SaaS Product Engineering (اقتراح فقط — لا تنفيذ)

> **قيد صارم**: لا تنفّذ مصادقة ولا قاعدة إنتاج ولا اشتراكات ولا فوترة حقيقية ضمن مهمة تجهيز المهارات هذه. المخرجات وثائق واقتراحات فقط حتى الاعتماد الصريح.

حين يُطلب تصميم مستقبل متعدد المستخدمين، اتبع هذا الـ skill. الأساس: التطبيق اليوم حالة عميل فقط بلا DB/مصادقة/اشتراكات.

## الوضع الحالي (الفجوات الموثقة)

- لا حفظ مشاريع (تُفقد عند التحديث)، لا سجل تصييرات، لا قوالب، لا لوحة استهلاك، و`/api/render` مفتوح بلا مصادقة (5/ساعة لكل IP).

## المكدس المقترح (متوافق Vercel — يُقيَّم قبل الالتزام)

| الطبقة | الاقتراح | البدائل الواجب تقييمها |
|---|---|---|
| مصادقة | Clerk (جاهز Next.js، خطط مجانية) | Auth.js، Supabase Auth — قارن التكلفة والتعقيد |
| قاعدة بيانات | Neon Postgres + Drizzle ORM (serverless، يتوقف للصفر) | Supabase Postgres، Vercel Postgres — قارن الإيقاف/التسعير |
| تخزين | Vercel Blob القائم بمسار `renders/{userId}/{renderId}.mp4` | — (موجود، أضف عزل المستخدمين) |
| فوترة | Stripe بنظام **كريدت** (1 تصيير = 1 كريدت) | — قيّم الباقات مقابل الاشتراك الثابت |
| حدود موزعة | Upstash Redis | Vercel KV — قارن مع `api-security-cost-protection` |
| مهام | Vercel Cron + جدول `renders` بحالة | طابور مخصص لاحقاً عند الحجم |

## نموذج البيانات المقترح (مسودة — لا migrations)

```
User       (clerkId UNIQUE, plan, credits, createdAt)
Project    (id, userId FK, title, theme, scenesJson, updatedAt)
Render     (id, projectId FK, status, url, durationSec, sandboxMs, creditsUsed, error)
UsageEvent (id, userId FK, kind: tts|image|render, units, at)
CreditTx   (id, userId FK, delta, reason, idempotencyKey UNIQUE, at)
```

## مبادئ ملزمة في التصميم

1. **الهوية قبل الخصوصية**: لا تُخزَّن مشاريع خاصة قبل `userId` موثوق + فحص ملكية خادم على كل قراءة/كتابة/حذف (`renders/{userId}/` + `WHERE userId`).
2. **الفوترة ليست تفويضاً**: الاستحقاق يُفحص خادماً عند كل عملية مكلفة (`credits ≥ cost` ثم خصم ذري) — لا تعتمد على حالة اشتراك في العميل.
3. **عدم ازدواج المعالجة**: كل حدث Stripe يُعالَج مرة واحدة (`idempotencyKey` على `event.id` + تحقق توقيع Webhook دائماً). الفشل يُعاد بأمان.
4. **الاحتفاط والحذف**: سياسة موثقة (مشاريع/renders/أصول Blob) + حذف حساب يحذف/يُجهل البيانات الخاصة.
5. **الهجرة**: `expand/contract` للأعمدة الإنتاجية (أضف → انقل → احذف) — لا إعادة تسمية/حذف مباشرة لعمود حي.

## سير العمل المقترح (عند الاعتماد — وليس الآن)

1. متطلبات المنتج (خطط/كريدت/حدود) → 2. schema + ملكية → 3. محاسبة استخدام ذرية → 4. Stripe webhooks (توقيع + عدم ازدواج) → 5. فرض مصادقة على `/api/render` أولاً (أعلى أثر تكلفة) → 6. حفظ مشاريع وسجل → 7. قوالب ولوحة استهلاك.

## معايير القبول للاقتراح

- يعكس التطبيق القائم (مساراته وحدوده وتكلفته) لا تطبيقاً نظرياً.
- يتضمن عزل البيانات، ومحاسبة محمية من التكرار، وفصل الفوترة عن التفويض، وتحليل تكلفة/خصوصية، واستراتيجية هجرة.
- يصرّح بما **لن** يُنفذ الآن.

## القيود والممنوعات

- ممنوع إنشاء جداول/هجرات إنتاجية أو تفعيل فوترة حية أو تخزين مشاريع خاصة قبل اعتماد البنية والمصادقة.
- ممنوع افتراض أن المصادقة وحدها تحمي البيانات — التفويض الخادم إلزامي.
- ممنوع اختيار Neon/Clerk/Stripe نهائياً دون مقارنة البدائل توثيقاً.
